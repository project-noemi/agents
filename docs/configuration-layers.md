# Configuration Layers for AGENTS.md

`AGENTS.md` is the upstream baseline that every copy of this repository shares. Organizations that run their own copy, for example an MSP/MSSP managing many customers, and those customers themselves, add rules **in separate layer files**, never by editing `AGENTS.md`. Upstream syncs then never collide with local rules, and every agent sees one explicit, ordered stack.

This guide covers the model, the files, the generator that wires the stack into Claude Code and Gemini CLI, how an MSP and a customer each add a layer, sync safety, and per-tool behaviour.

## The four-layer model

| # | Layer | Typical path | Owned by | Committed? |
|---|-------|--------------|----------|------------|
| 1 | Upstream baseline | `AGENTS.md` | project-noemi/agents | Yes (upstream) |
| 2 | MSP / MSSP layer | `org/<msp>/AGENTS.md`, e.g. `org/newpush/AGENTS.md` | The managing company | Yes (vendored read-only into customer repos) |
| 3 | Customer layer | `org/<customer>/AGENTS.md` | The customer repository | Yes (customer repo only) |
| 4 | Local layer | `AGENTS.local.md` | One machine or user | **No**, gitignored |

Layers 2 and 3 are selected by a committed manifest, `AGENTS.layers`. A repository may list fewer layers (an MSP's own fork lists only its MSP layer) or more (a customer with a business-unit layer). The manifest decides; the table shows the intended hierarchy.

## Load order and precedence

1. `AGENTS.md`.
2. Each path in `AGENTS.layers`, top to bottom. If the environment variable `NOEMI_ORG_LAYERS` is set and non-empty, its comma-separated paths **replace** the manifest for that session.
3. `AGENTS.local.md`, if it exists. It always loads last.

On any conflict, **the later source wins**. A listed file that does not exist is a no-op, not an error, so a manifest can list a layer before it is vendored in.

Layers should say what they replace. The template [`org/example/AGENTS.md`](../org/example/AGENTS.md) has an **Overrides of earlier layers** section for that, so agents never have to infer which of two contradictory rules applies.

## Files

### `AGENTS.layers` (manifest, committed downstream)

```text
# MSP layer (vendored read-only)
org/newpush/AGENTS.md
# Customer layer (ours)
org/acme/AGENTS.md
```

- One repo-relative path per line. `#` starts a comment, either for the whole line or after whitespace.
- Paths must stay inside the repository: no absolute paths, no `~`, no `..`, no backslashes, no whitespace, no leading `@`. Markdown files only.
- Do not list `AGENTS.md` (always first), `AGENTS.local.md` (always last) or `AGENTS.override.md` (see the Codex notes below).
- Upstream ships [`AGENTS.layers.example`](../AGENTS.layers.example) as the format reference and **no live `AGENTS.layers`**. Downstream repos copy the example to `AGENTS.layers`.

### `NOEMI_ORG_LAYERS` (session override)

`NOEMI_ORG_LAYERS="org/acme/AGENTS.md,org/acme-ci/AGENTS.md"` replaces the manifest for one process, for example in CI or while testing a new layer. Unset or blank means "use the manifest". The same well-formedness rules apply.

### `AGENTS.local.md` (gitignored)

This file holds personal or machine-specific preferences, such as a preferred test command or a local sandbox URL. It is listed in `.gitignore` and must never hold secrets; the SecretOps rules apply to it like any other file.

### Layer files

Start from [`org/example/AGENTS.md`](../org/example/AGENTS.md). Write deltas, not a copy of the baseline. Keep each layer short, because every layer loads into every session.

## Generated imports for Claude Code and Gemini CLI

`@AGENTS.layers` would import only the *list of paths*, not the files it names. So the stack is expanded by the existing context generator, `scripts/generate_all.js`, through `scripts/context_layers.js`:

```bash
npm run generate            # same as: node scripts/generate_all.js
```

The generator resolves `AGENTS.layers` (or `NOEMI_ORG_LAYERS`), skips listed files that do not exist, appends `AGENTS.local.md` if present, and writes `CLAUDE.md` and `GEMINI.md` as:

```text
@AGENTS.md

<!-- BEGIN NOEMI CONFIGURATION LAYERS: generated by scripts/generate_all.js from AGENTS.layers / NOEMI_ORG_LAYERS / AGENTS.local.md. Do not edit; re-run `npm run generate`. -->
@org/newpush/AGENTS.md
@org/acme/AGENTS.md
@AGENTS.local.md
<!-- END NOEMI CONFIGURATION LAYERS -->
```

- **No layers resolve** (the upstream case: no live `AGENTS.layers`, no `AGENTS.local.md`): the block is omitted and both files stay exactly `@AGENTS.md`, as Decision [2026-09-22-0001] requires.
- **Idempotent:** both files are fully regenerated from the same inputs, so re-running produces identical bytes. Never edit inside the markers.
- **Malformed paths fail the run** with the offending line. Missing files only print a "skipped" note.
- **Re-run it** after editing `AGENTS.layers`, after vendoring or removing a layer, and after every upstream or MSP sync. CI (`validate.yml`) regenerates and fails if the committed `CLAUDE.md`/`GEMINI.md` are stale, and `npm run audit` checks them against the expected output.
- **Do not commit session-specific output.** If `AGENTS.local.md` exists or `NOEMI_ORG_LAYERS` is set, the generator warns: the regenerated files then import your local file or the override stack. Commit `CLAUDE.md`/`GEMINI.md` only as generated from the committed manifest. CI has neither file nor variable, so a stray `@AGENTS.local.md` line fails the freshness check.

Codex, Cursor and other tools do not expand `@` imports. For them, the plain-text instruction at the end of `AGENTS.md` (section **Configuration layers**) tells every agent to read `AGENTS.layers`, each listed file, then `AGENTS.local.md`, with its file tools.

## How an MSP adds its layer

In the MSP's own copy of this repository (for example `newpush/newpush-agents`, synced from upstream with `scripts/sync-upstream.sh`):

1. Copy the template: `mkdir -p org/newpush && cp org/example/AGENTS.md org/newpush/AGENTS.md`, then write the MSP's rules.
2. `cp AGENTS.layers.example AGENTS.layers` and list only `org/newpush/AGENTS.md`.
3. `npm run generate`, then `npm run validate`. Commit `org/newpush/`, `AGENTS.layers`, `CLAUDE.md` and `GEMINI.md` through the normal reviewed PR flow.

### Publishing the layer to customers

Customers need **only the layer directory**, not the MSP's whole repository. Do **not** tell customers to run `git subtree add --prefix=org/newpush <msp-fork-remote> main`: that copies the *entire* MSP fork (baseline, scripts, every file) into `org/newpush/`. Publish the layer on its own instead, in one of two ways:

**Option A (recommended): a dedicated layer repository**, for example `newpush/agents-org-newpush`, with the layer's `AGENTS.md` at its root. It is small, can be granted read-only to customers without exposing the MSP's fork, and has its own review history. The MSP's fork can consume it the same way customers do (see below), so the layer has one source of truth.

**Option B: a `git subtree split` branch** cut from the MSP fork, holding only `org/newpush/` re-rooted:

```bash
# In the MSP fork, after the layer change has merged:
git subtree split --prefix=org/newpush -b org-newpush-layer
git push <layer-remote> org-newpush-layer:main     # e.g. the Option A repo
```

Either way, the published tree contains only the layer files (`AGENTS.md` plus anything it imports), with no secrets and no customer data.

## How a customer adds theirs

The cleanest topology is for the customer repository to sync the baseline from upstream directly and vendor only the MSP layer:

```bash
# 1. Baseline: a copy of project-noemi/agents, synced with scripts/sync-upstream.sh.

# 2. MSP layer: subtree ONLY the published layer into org/<msp>/.
git remote add msp-layer https://github.com/newpush/agents-org-newpush.git
git subtree add  --prefix=org/newpush msp-layer main --squash
# Later updates:
git subtree pull --prefix=org/newpush msp-layer main --squash

# 3. Customer layer: owned here.
mkdir -p org/acme && cp org/example/AGENTS.md org/acme/AGENTS.md   # then edit

# 4. Manifest (order = precedence), then regenerate and validate.
cp AGENTS.layers.example AGENTS.layers   # edit: org/newpush/AGENTS.md, then org/acme/AGENTS.md
npm run generate && npm run validate
```

Rules for customers:

- Never edit `org/<msp>/` in the customer repo. A local edit turns the next `subtree pull` into a conflict. Put disagreements in `org/<customer>/AGENTS.md` under **Overrides of earlier layers**.
- `AGENTS.layers` belongs to the customer. The MSP may document the line to add, but it does not ship the customer's manifest.

A customer *can* instead copy the MSP's fork and sync from it. Then `org/<msp>/` arrives with the ordinary sync, but the MSP's own `AGENTS.layers` collides with the customer's on every sync (`-X ours` keeps the customer's copy, which silently drops new MSP manifest lines). Prefer the topology above.

## Sync safety

Each path has exactly one owner, so no sync writes to another owner's files:

| Path | Written by | Upstream sync | MSP layer pull | Customer |
|------|-----------|---------------|----------------|----------|
| `AGENTS.md`, `AGENTS.layers.example`, `org/example/`, scripts, docs | Upstream | Updates | Never touches | Does not edit |
| `org/<msp>/` | MSP | Never touches (upstream never ships it) | Updates | Does not edit |
| `org/<customer>/`, `AGENTS.layers` | Customer | Never touches (upstream ships no live manifest) | Never touches | Owns |
| `AGENTS.local.md` | Developer | Gitignored | Gitignored | Gitignored |
| `CLAUDE.md`, `GEMINI.md` | Generator | May update | n/a | Re-run `npm run generate` |

- `scripts/sync-upstream.sh` merges with `-X ours` and lists every overridden file in the PR body. A layered downstream normally overrides nothing except possibly `CLAUDE.md`/`GEMINI.md`. Regenerate them on the sync branch before merging.
- Upstream reserves `org/` for downstream layers and ships only `org/example/`. Do not name your organization `example`.
- If an upstream change ever rewrites the **Configuration layers** section, take the upstream version. Downstream copies should not edit that section either; local rules belong in layers.

## Tool notes

### Claude Code

- With a `CLAUDE.md` present, Claude Code reads `CLAUDE.md` (not `AGENTS.md` directly). `CLAUDE.md` imports `AGENTS.md` and the generated layer block, so the layers load deterministically at launch, in order.
- Imports resolve relative to the importing file. Block-level HTML comments, including the BEGIN/END markers, are stripped before loading.
- Claude Code does not read `AGENTS.local.md` natively; the generated `@AGENTS.local.md` line is what loads it. A personal `CLAUDE.local.md` still works and loads after `CLAUDE.md`.

### Gemini CLI

- `GEMINI.md` is the default context file; its `@` imports, nested ones included, are processed at load.
- A missing import produces an error comment in context. The generator skips missing files, so after deleting a layer, re-run `npm run generate` to drop its import.

### Codex

- Codex concatenates `AGENTS.md` files from the repository root down to the working directory, at most one file per directory. It **does not expand `@` imports**, so the layers load only because the agent follows the instruction in `AGENTS.md` and reads them with its file tools.
- **Never use `AGENTS.override.md` for layers.** In any directory, Codex reads `AGENTS.override.md` *instead of* `AGENTS.md`, so a root override **replaces the upstream baseline** entirely. Reserve it for deliberate replacement; the layer tooling rejects it in `AGENTS.layers`.
- **Size cap:** Codex stops adding instruction files once the combined size reaches `project_doc_max_bytes`, **32 KiB by default**, and silently truncates beyond that. The root `AGENTS.md` counts against it. Layers that the agent reads with file tools do not, but keep them short anyway. To raise the cap, set `project_doc_max_bytes` in `~/.codex/config.toml`.
- A layer file named `org/<x>/AGENTS.md` is also picked up natively when Codex runs *inside* `org/<x>/`. That is harmless, but it is not how layers apply repository-wide; the manifest is.

### Cursor

- Cursor loads the root `AGENTS.md` as plain text and treats `@` as a reference, not an expansion. Like Codex, it relies on the instruction to read `AGENTS.layers` and each listed file.
- Nested `AGENTS.md` files apply to their own directories, so `org/<x>/AGENTS.md` also scopes itself to edits inside `org/<x>/`. That is harmless and does not replace the manifest.

### Any other tool

Any tool that loads `AGENTS.md` as text gets the same instruction. Ask it to "list the instruction files you loaded" to confirm the stack.

## CI checks

`npm run audit` (run by `validate.yml`) enforces a light contract through `scripts/context_layers.js`:

- `AGENTS.md` ends with a top-level `# Configuration layers` section that names `AGENTS.layers`, `NOEMI_ORG_LAYERS` and `AGENTS.local.md`.
- `org/example/AGENTS.md` exists.
- Every path in `AGENTS.layers` and `AGENTS.layers.example` (whichever exist) is well-formed: relative, inside the repository, `.md`, not reserved, no duplicates.
- `.gitignore` ignores `AGENTS.local.md`.
- `CLAUDE.md`/`GEMINI.md` equal the generator's output for this checkout.

Listed layer files that are **missing do not fail the build**. Tests live in `tests/config-layers.test.js`.

## Risks

- **Agents skipping the read step** (Codex, Cursor): keep the instruction at the end of `AGENTS.md`, keep layers short, and spot-check with "which instruction files did you load?".
- **Stale generated imports:** re-run `npm run generate` after any manifest or layer change. CI catches committed staleness.
- **Context growth:** every layer loads every session; the Codex cap is 32 KiB by default.
- **Ownership drift:** editing a vendored MSP layer in a customer repo breaks subtree pulls. Use the customer layer instead.
