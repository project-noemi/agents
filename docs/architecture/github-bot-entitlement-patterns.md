# Pair the App install with a registry

Every tool studied, from Dependabot and Renovate to Copilot's coding agent and Devin, treats a GitHub App installation as the **ceiling** on what a bot may touch. None treats it as the **grant**. Work starts only when the installation is also bound to a vendor-side account, seat or opt-in, and a person with write access triggers the run. That one fact decides NewPush's proposal. "Entitled if noemi-conductor is installed" cannot stand alone, because an App that installs on client orgs must be **public**, and a public App can be installed by anyone. Under the proposal, any stranger's org could spend the shared NewPush budget. The industry-standard minimum is not a tenant file per client and not client API keys. It is a small registry keyed by GitHub installation and account IDs, intersected with the live installation. That registry holds per-client caps against the one shared NewPush pool, and it sits alongside five controls: write-access trigger authorization, a bot author with the requesting human as co-author, webhook-driven uninstall and suspend handling, CI held until a human approves, and defenses against untrusted issue text. The proposal's instincts are right and match industry practice: one budget, one App, installation as the source of truth for repo scope, and BYO-App only for self-hosting. It needs that registry row and those five controls before noemi-conductor can safely be made public.

## Installation is the ceiling; a vendor-side binding is the grant

GitHub's platform guidance is clear about the credential. For any long-lived integration acting on an org's behalf, GitHub recommends building a GitHub App over OAuth apps or PATs, and says an App "should never use a personal access token or GitHub password to authenticate" ([GitHub Docs](https://docs.github.com/en/apps/creating-github-apps/about-creating-github-apps/deciding-when-to-build-a-github-app); [Best practices](https://docs.github.com/en/apps/creating-github-apps/about-creating-github-apps/best-practices-for-creating-a-github-app)). On install, an org owner picks **"All repositories" or "Only select repositories"**. Repo admins can install only Apps that request no org-level permissions, and org owners can turn even that off ([GitHub Docs](https://docs.github.com/en/apps/using-github-apps/installing-a-github-app-from-a-third-party); [GitHub Docs](https://docs.github.com/en/organizations/managing-programmatic-access-to-your-organization/limiting-oauth-app-and-github-app-access-requests)). Installation access tokens **expire after one hour** and can be narrowed per request to named repos and a subset of permissions. They can never go beyond what the installation granted ([GitHub Docs](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/generating-an-installation-access-token-for-a-github-app)). That gives the installation a real role: it is the hard outer boundary that the client controls.

The decisive constraint is visibility. A private App "can only be installed on the account that owns the app." Any App that NewPush wants to install on a client org must therefore be public, and any GitHub user can install a public App ([GitHub Docs](https://docs.github.com/en/apps/creating-github-apps/registering-a-github-app/making-a-github-app-public-or-private)). It can stay unlisted from Marketplace, but the research found **no native way to restrict who installs a public App**, such as an invite token. GitHub also says a public App cannot be made private again once it is installed on other accounts ([GitHub Docs](https://docs.github.com/en/apps/maintaining-github-apps/modifying-a-github-app-registration)). So "installed ⇒ entitled" really means "anyone who clicks Install ⇒ entitled to NewPush's model budget." Today noemi-conductor works because it is presumably private to NewPush and the static `orgs` list happens to match the only places it can be installed. Making it public removes that coincidence.

Every vendor closes this gap the same way: a second key on the vendor side. Cursor binds each installation to exactly one Cursor team. A second claimant gets "GitHub installation is already connected to another Cursor target," and "Protected Git Scopes" lock a GitHub org to one Cursor org ([Cursor Docs](https://cursor.com/docs/integrations/github)). For Devin, "only members of the organization that installed the integration can use it," and enterprises assign repos to specific Devin orgs ([Devin Docs](https://docs.devin.ai/integrations/gh)). Snyk configures the App per Snyk Organization, and it needs both a Snyk Org Admin and a GitHub Org Admin ([Snyk Docs](https://docs.snyk.io/developer-tools/scm-integrations/organization-level-integrations/github-cloud-app)). CodeRabbit requires a GitHub login and an org subscription, and gives full reviews only to seated PR authors ([CodeRabbit Docs](https://docs.coderabbit.ai/platforms/github-com); [Seat assignment](https://docs.coderabbit.ai/management/seat-assignment)). Copilot's agent depends on plan and org policy, and repo admins can still switch it off per repo ([GitHub Docs](https://docs.github.com/en/copilot/concepts/agents/coding-agent/about-coding-agent)). Dependency bots add a third key, in-repo consent. Renovate "makes no other changes and opens no other PRs until you merge the onboarding PR," so merging is consent and closing is a reversible refusal ([Renovate Docs](https://docs.renovatebot.com/getting-started/installing-onboarding/)). Dependabot runs only where a `dependabot.yml` is committed ([GitHub Docs](https://docs.github.com/en/code-security/dependabot/dependabot-version-updates/about-dependabot-version-updates)). Self-hosted Renovate makes the model explicit: what it may touch is the intersection of the installation's repos, the operator's `autodiscoverFilter`, and the repo's opt-in ([Renovate self-hosted config](https://docs.renovatebot.com/self-hosted-configuration/)).

The pattern is clear. Entitlement equals **installation ∩ vendor registry ∩ (optionally) per-repo opt-in**, and a bare install is never enough.

| Tool | Outer boundary | Vendor-side binding | Per-repo / per-user gate |
|---|---|---|---|
| Copilot coding agent | GitHub plan + org policy | Copilot seat of triggering user | Per-repo disable; write-access trigger |
| Devin | App install (all/select) | Installation → one Devin org; enterprise repo assignment | Write access **and** linked Devin account |
| Cursor | App install (all/select) | Installation → exactly one team; Protected Git Scopes | Cloud-Agents plan + repo write |
| Renovate (Mend / self-hosted) | App install (all/select) | Mend portal org / `autodiscoverFilter` | Onboarding PR merge |
| Snyk | App install | Snyk Organization | Project import |
| CodeRabbit | App install | Org subscription | Seat per PR author |
| claude-code-action | Workflow file committed in repo | Repo secret (BYO key) | Write-access trigger |

## Who may pull the trigger matters more than which org is listed

Entitlement decides where the bot may act. Trigger authorization decides who may spend money making it act, and here the industry has a single answer. On Copilot, "only users with write access to the repository can trigger Copilot cloud agent," and "comments from users without write access are never presented to the agent" ([GitHub Docs](https://docs.github.com/en/copilot/concepts/agents/cloud-agent/risks-and-mitigations)). Claude Code GitHub Actions checks write access on every issue, PR, comment and review event, and blocks bots by default. It labels its `allowed_non_write_users` escape hatch RISKY because it "bypasses the primary security mechanism" ([claude-code-action security.md](https://github.com/anthropics/claude-code-action/blob/main/docs/security.md)). Devin requires write or admin **plus** a linked Devin account, and ignores comments on issues and closed PRs ([Devin Docs](https://docs.devin.ai/integrations/gh)). Label- and assignment-based triggers are write-gated by GitHub itself, because only triage or write users can apply labels. That makes them safer than mention triggers. Sweep's old "issue titled `Sweep:`" trigger let any issue author start paid work, which is the anti-pattern ([sweepai/sweep](https://www.Github.com/sweepai/sweep)).

Billing follows the vendor tenant or the triggering seat, never the raw GitHub org. Copilot charges one premium request per session, times the model multiplier, to the triggering user, and caps sessions at **59 minutes** that "cannot be extended or bypassed" ([GitHub Docs](https://docs.github.com/en/copilot/concepts/billing/copilot-requests); [GitHub Docs](https://docs.github.com/en/copilot/concepts/agents/coding-agent/about-coding-agent)). Cursor bills shared-installation usage to the team that receives the share ([Cursor Docs](https://cursor.com/docs/integrations/github)). Mend sets per-org capacity tiers, for example **1 / 2 / 16 concurrent jobs** and 30–60 minute job timeouts across Community, OSS and Enterprise ([Mend-hosted overview](https://docs.renovatebot.com/mend-hosted/overview/)). Jules caps individuals at **15 tasks per day and 3 concurrent** on the free tier ([Jules Docs](https://jules.google/docs/usage-limits/)). This is where the user's preference is well supported. No vendor makes clients bring their own model keys for the hosted product. Only the self-hosted claude-code-action path does that ([claude-code-action security.md](https://github.com/anthropics/claude-code-action/blob/main/docs/security.md)). A single NewPush pool is normal. What every vendor adds is attribution and per-tenant caps inside the pool, so one client cannot drain capacity for the others. GitHub's own rate limits already work this way, at **5,000 requests per hour per installation**, scaling to 12,500 ([GitHub Docs](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api)). Under today's `tenants/internal.json`, a new client would share the single 50 USD/day, 3-concurrent-job pool with no per-client ceiling.

Identity has an equally settled reference design. Copilot authors commits as Copilot and lists the requesting developer as co-author. It signs the commits, links each to its session log, and bars the requester from approving the PR. It requires an extra approval when no human is attributed, and it does not run Actions workflows on agent code until a write-access user approves ([GitHub Docs](https://docs.github.com/en/copilot/concepts/agents/cloud-agent/risks-and-mitigations)). Renovate, Snyk, CodeRabbit and Codecov all act as `<app-slug>[bot]` with installation tokens. Snyk names "rather than going through a service account" as a benefit of its move to the App ([Snyk Docs](https://docs.snyk.io/developer-tools/scm-integrations/organization-level-integrations/github-cloud-app); [Renovate Docs](https://docs.renovatebot.com/modules/platform/github/)). Dependabot goes further. Workflows triggered by `dependabot[bot]` get a read-only `GITHUB_TOKEN` and no Actions secrets ([GitHub Docs, GHES 3.17](https://docs.github.com/en/enterprise-server@3.17/code-security/reference/supply-chain-security/dependabot-on-actions)).

## The noemi-agent machine account will not travel to client orgs

NewPush currently opens PRs from **noemi-agent**, a machine user, while noemi-conductor (an App) reads issues and comments. That split works inside NewPush's own orgs and breaks at a client's door in three ways. First, on paid plans an outside collaborator on a private repo "will use one of your paid licenses," so every client would pay a seat for NewPush's bot, and it must meet the client's 2FA policy ([GitHub Docs](https://docs.github.com/en/organizations/managing-user-access-to-your-organizations-repositories/managing-outside-collaborators/adding-outside-collaborators-to-repositories-in-your-organization)). GitHub Apps "do not consume a seat" ([GitHub Docs](https://docs.github.com/en/apps/creating-github-apps/about-creating-github-apps/deciding-when-to-build-a-github-app)). Second, Enterprise Managed Users "cannot be invited to organizations or repositories outside of the enterprise." No github.com account, machine user or PAT can be added to an EMU client at all, while an App that a client org owner installs works there ([GitHub Docs](https://docs.github.com/en/enterprise-cloud@latest/admin/managing-iam/understanding-iam-for-enterprises/abilities-and-restrictions-of-managed-user-accounts)). Third, GitHub's Terms allow "no more than one free machine account in addition to your free Personal Account," with a named human responsible for it. That rules out scaling to one machine user per client ([GitHub ToS](https://docs.github.com/en/site-policy/github-terms/github-terms-of-service)). The research did not verify whether corporate-terms plans relax that limit.

The App is therefore the only identity that works the same way across EMU and non-EMU clients. It also brings per-installation rate-limit isolation, which a single machine-user token shared across every client lacks ([GitHub Docs](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api)). For client repos, PRs should be opened with a noemi-conductor installation token (or a sibling noemi-agent App), authored as `<slug>[bot]` with the App's noreply email, as Renovate documents ([Renovate Docs](https://docs.renovatebot.com/modules/platform/github/)). The noemi-agent machine user can stay on NewPush-owned orgs, where it already has membership. One caution: the App's single private key "grants access to every account that the app is installed on" ([GitHub Best practices](https://docs.github.com/en/apps/creating-github-apps/about-creating-github-apps/best-practices-for-creating-a-github-app)). Once clients install it, that PEM becomes NewPush's highest-value secret and must stay vault-only under the fetch-on-demand policy.

## Untrusted issue text is the attack path, even with a trusted trigger

Write-gating the trigger is necessary and not sufficient. In Trail of Bits' August 2025 demonstration, an outsider filed a public issue and a trusted maintainer assigned it to Copilot. The payload was hidden in `<picture>`/`<source>` HTML, invisible in the UI but read by the model. It made the agent add a malicious wheel URL to `uv.lock` and run `curl … | sh`. The egress firewall did not stop it because `raw.githubusercontent.com` was allowlisted, and human review missed it because maintainers rarely read lock-file URLs ([Trail of Bits](https://blog.trailofbits.com/2025/08/06/prompt-injection-engineering-for-attackers-exploiting-github-copilot/)). Later incidents follow the same pattern. In "Clinejection" (February 2026), a malicious issue title against an AI triage workflow led to stolen publishing credentials and a tampered npm release ([CSA](https://labs.cloudsecurityalliance.org/research/csa-research-note-clinejection-prompt-injection-cicd-cache-p/)). "GitLost" used public issues to make agentic workflows leak private-repo data ([InfoQ](https://infoq.com/news/2026/07/gitlost-github-prompt-injection)). The research team read only secondary write-ups of the 2026 incidents, so their details should be checked against primary sources.

Vendors stack the same defenses. Copilot strips hidden characters and HTML comments, runs behind a firewall, and can push only to its own branch with restricted credentials. It runs CodeQL, dependency checks and secret scanning on its output ([GitHub Docs](https://docs.github.com/en/copilot/concepts/agents/cloud-agent/risks-and-mitigations)). claude-code-action strips HTML comments, invisible characters, image alt text and hidden attributes, but warns that "new bypass techniques may emerge." On `pull_request_target`, it restores `.claude/`, `CLAUDE.md` and `.mcp.json` from the base branch, yet leaves `package.json`, lockfiles and Makefiles at PR head ([claude-code-action security.md](https://github.com/anthropics/claude-code-action/blob/main/docs/security.md)). Codex states that review rules "don't replace tests, branch protections, or required approvals" ([Codex Docs](https://learn.chatgpt.com/docs/third-party/github)). Each layer has been bypassed at least once, which is why vendors stack them and why the human CI and merge gate remains the backstop. The noemi loop already scans issue bodies before acting (the `--scan` gate). Moving to client orgs raises the stakes: their repos will hold issues written by people NewPush has never vetted.

## Recommendations for the noemi coding loop

The user's proposal survives with one change and several additions. Keep one App, one shared NewPush budget, installation-derived repo scope, and BYO-App only for self-hosted runs. Replace "installed ⇒ entitled" with **"installed AND registered ⇒ entitled."** The registry is not a tenant file per client. It is a row per client, sitting in the store that already holds tenant config, keyed by the IDs GitHub says to use. GitHub explicitly warns against keying on "user handles, organization slugs, or email addresses" ([GitHub Best practices](https://docs.github.com/en/apps/creating-github-apps/about-creating-github-apps/best-practices-for-creating-a-github-app)). Today's `tenantAllows()` matches on org slug strings, which a rename would silently break or, worse, hand to whoever claims the old name.

| Priority | Change | Industry precedent | What it replaces / avoids |
|---|---|---|---|
| **P0** | Entitlement = live installation (`GET /repos/{owner}/{repo}/installation` or webhook-maintained cache) **∩** registry row `{installation_id, account_id, client_name, status, daily_usd_cap, concurrent_cap, repos?}`. Unregistered installs: refuse with a visible "not onboarded" comment and alert NewPush. | Cursor one-target binding, Devin org membership, Snyk Org, Renovate `autodiscoverFilter` | Replaces the `orgs` slug list; avoids "any installer spends our budget" |
| **P0** | Trigger authorization: act only on a `noemi:*` label or assignment, or on a `/noemi` mention whose author has write+ on the repo (`collaborators/{user}/permission`). Drop non-write comments from model context. Deny bots unless explicitly allowlisted. | Copilot, claude-code-action, Devin | No author-permission check found in `coding-loop/*.js` today |
| **P0** | Open client PRs as the App bot (installation token narrowed to the one repo, minimal permissions, one hour), with `Co-authored-by:` the triggering human and "Requested by @user" in the PR body. Keep the noemi-agent machine user for NewPush orgs only. | Copilot, Renovate, Snyk | Avoids outside-collaborator seats, EMU incompatibility, ToS machine-account limit |
| **P1** | Handle `installation.created` (create a pending row, never auto-activate), `deleted` (cancel jobs, purge tokens, mark offboarded), `suspend`/`unsuspend` (pause/resume), and `installation_repositories.removed`. Reconcile nightly via `GET /app/installations`. Use owner-side `PUT /app/installations/{id}/suspended` as the per-client kill switch. | GitHub platform guidance | Static list never learns of uninstalls |
| **P1** | Per-client caps inside the one NewPush pool (e.g. daily USD and concurrent jobs per registry row, plus a hard per-run timeout), with every run attributed to installation, repo, issue and triggering user in the audit log. | Mend per-org quotas, Jules caps, Copilot 59-min limit, Cursor billed-to-team | Keeps one budget; avoids per-client API keys |
| **P1** | Make the `noemi-code /issue` path pass `--tenant` (or resolve tenant from the installation) and surface intake refusal reasons to the operator. | Devin/Copilot visible refusals | Hidden "outside-tenant" refusals |
| **P1** | Hold CI on agent PRs until a write-access human approves; give bot-triggered workflows no elevated secrets; require a non-requester approval; flag lockfile and dependency-source changes for explicit review. | Copilot, Dependabot restricted token, Trail of Bits finding | Agent code running with secrets before review |
| **P2** | Untrusted-input hygiene: strip hidden HTML, comments, alt text and invisible characters before the model sees them; tight egress allowlist (no blanket `raw.githubusercontent.com`); load agent config (`CLAUDE.md`, MCP config) from the base branch only. | Copilot, claude-code-action | Extends the existing `--scan` gate |
| **P2** | Optional per-repo consent: require a `.github/noemi.yml` file or an onboarding PR before first action, for clients who installed on "All repositories." | Renovate onboarding PR, Dependabot config file | Lets a client's repo maintainers opt out without an org owner |
| **P2** | Self-hosted / BYO-App mode: client registers its own App (manifest flow returns `id`, `pem`, `webhook_secret` straight to vault), and the loop reads `{app_id, private_key_ref, api_base_url}` from the run config. Same code path; the client's runner pays its own model cost only in this mode. | Renovate self-hosted, Codecov `integration.id`/`pem`, Probot | Keeps BYO keys out of the hosted product |

Two forks deserve an explicit decision. The first is how much the registry has to hold. At minimum it needs one row per client with an active or suspended flag and two cap numbers, which is far lighter than today's tenant JSON with its vault and model blocks. It is still a deliberate onboarding step, and the evidence says it cannot be skipped: every vendor studied has one, and the public-App constraint makes it a security control rather than paperwork. A middle path is to auto-create a **pending** row on `installation.created` and have a NewPush human flip it to active. That keeps onboarding to a single click on NewPush's side. The second fork is whether client repos need in-repo consent on top of org-owner installation. For an MSP with a contract, the owner's "Only select repositories" choice is defensible consent on its own. A config-file opt-in becomes worth it mainly for clients who pick "All repositories."

## Conclusion

The research turns the proposal from "trust the install" into "trust the install, then verify the installer." GitHub's design pushes every multi-tenant bot toward the same shape. The client controls scope through installation, the vendor controls spend through an ID-keyed registry, and repo collaborators control triggering through write access. Making noemi-conductor public is the step that turns NewPush's slug allowlist from adequate into dangerous, because the App's audience becomes everyone on GitHub, so the registry needs to ship before or with that step, not after. The user's two red lines hold up against industry practice. No hosted vendor asks clients for their own model keys, and none keeps a config file per customer in source control.

A second implication is less obvious. Moving client work from the noemi-agent machine user to App identity is more than tidying. It is what makes EMU clients reachable at all, and it turns per-client revocation into something GitHub enforces (uninstall, suspend, repo removal) instead of a NewPush promise. The remaining open risk is the one no vendor has solved: prompt injection in issue bodies written by outsiders and passed along by trusted maintainers. For client work, the human gate on CI and merge is load-bearing and should not become optional.
